# rep-mind-map

CLI-инструмент: одной командой строит интерактивный граф зависимостей JS/TS-проекта — до уровня функций и классов, локально и без настройки.

```
npx rep-mind-map <путь к папке проекта>
```

Команда анализирует проект, сохраняет один самодостаточный `index.html` и открывает его в браузере. Дальше пользователь работает с графом в браузере: двигает, приближает, раскрывает узлы, смотрит связи.

Источник требований — презентации итераций 2–7 (BR-1…BR-4, FR-1…FR-6, атрибуты качества, спецификация UC01). Если код и этот файл расходятся с ними, сначала спросить, а не выбирать самому.

## Стек

- Node.js ≥ 18, TypeScript, ESM (`"type": "module"`).
- Разбор кода — `ts-morph`.
- Отрисовка графа — D3.js (SVG, force simulation, drag, zoom).
- Тесты — Vitest. Линтер — ESLint. Менеджер пакетов — npm.

## Команды

Запускать из корня репозитория:

- `npm run build` — сборка
- `npm test` — тесты (Vitest)
- `npm run lint` — ESLint
- `npm run typecheck` — проверка типов (`tsc --noEmit`)
- `npm start -- <путь>` — запуск собранного CLI на проекте

## Архитектура

Синхронный конвейер из пяти модулей (итерация 4). Каждый модуль — своя папка в `src/`:

| Модуль | Папка | Что делает | Требования |
|---|---|---|---|
| CLI | `src/cli` | Принимает аргументы, запускает конвейер, выводит ход работы и итог, открывает браузер | FR-5 |
| Parser | `src/parser` | Находит и читает `.ts`/`.js` файлы, строит AST через ts-morph, извлекает модули, классы, функции, методы, импорты и вызовы | FR-1 |
| Graph Builder | `src/graph` | Строит граф `{ nodes, edges }`, определяет состояние связей, ищет циклы | FR-2, FR-4 |
| HTML Generator | `src/html` | Упаковывает граф, код отрисовки и стили в один `index.html` | FR-6 |
| Renderer | `src/renderer` | Код, который работает в браузере: рисует граф на D3, обрабатывает клики | FR-3 |

Правила границ между модулями:

- У каждого модуля есть `index.ts` — его публичная часть. Другие модули импортируют только из `index.ts`, а не из внутренних файлов модуля.
- Данные между модулями передаются только в виде типов из `src/shared` (контракт `{ nodes, edges }` и доменные типы). Внутренние структуры модуля наружу не выходят.
- Типы ts-morph не выходят за пределы `src/parser`. Наружу Parser отдаёт только наши доменные типы. Так разбор кода можно заменить, не трогая остальное.
- `src/renderer` — код для браузера: в нём нельзя импортировать Node.js-модули (`fs`, `path` и т. п.) и код из других модулей, кроме типов из `src/shared`.
- Зависимости между модулями идут в одну сторону: CLI → Parser → Graph Builder → HTML Generator. Renderer только читает граф из страницы.

## Обязательные свойства системы

Это гарантии из спецификации UC01 и атрибутов качества. Нарушать нельзя.

- **Никакой сети.** Код не делает сетевых запросов: ни во время анализа, ни в готовой странице. D3 и стили встраиваются в `index.html`, без CDN.
- **Файлы анализируемого проекта не изменяются.** Только чтение. Писать можно только итоговую страницу.
- **Ошибка в одном файле не останавливает анализ.** Файл пропускается и попадает в список ошибок разбора (поток 4А).
- **Результат — один самодостаточный `index.html`**, который открывается без сервера.
- Без базы данных: анализ без состояния, каждый запуск независим.
- Только JavaScript и TypeScript (ES2015+).

## Глоссарий: понятие → имя в коде

Имена в коде на английском. При появлении нового понятия добавить строку сюда.

| Понятие | В коде |
|---|---|
| Проект | `Project` |
| Исходный файл | `ProjectFile` (не `SourceFile` — это имя занято классом ts-morph) |
| Элемент кода (абстрактный) | `CodeElement` |
| Модуль / Класс / Функция / Метод | `ModuleElement` / `ClassElement` / `FunctionElement` / `MethodElement` |
| Зависимость | `Dependency` |
| Вид зависимости: импорт / вызов | `DependencyKind`: `"import"` / `"call"` |
| Состояние зависимости: корректная / сломанная / циклическая | `DependencyState`: `"valid"` / `"broken"` / `"cyclic"` |
| Цикл зависимостей | `DependencyCycle` |
| Ошибка разбора | `ParseError` |
| Отчёт анализа | `AnalysisReport` |
| Граф проекта | `ProjectGraph` (узлы `GraphNode`, рёбра `GraphEdge`) |

## Правила кода

- В классах всегда явный `constructor()`, поля инициализируются внутри него. Field initializers (`field = value` в теле класса) не использовать.
- Вместо `Record<K, V>` писать index signature: `{ [key: string]: T }`.
- Типы объявлять через `type`. `interface` не использовать.
- Параметры функций — простые значения с понятными именами: `parseProject(projectPath: string)`. Объекты-параметры с типом прямо в сигнатуре (`({ path }: { path: string })`) не использовать.
- Если функции всё-таки нужен объект, его тип описывается заранее отдельным `type`, а в функцию передаётся переменная с понятным именем: `buildGraph(parseResult: ParseResult)`.
- Константы:
  - Переменные объявлять через `const`, `let` использовать редко.
  - Имена констант всегда в camelCase, как у обычных переменных. `UPPER_SNAKE_CASE` не использовать.
  - Настраиваемые числовые параметры класса — поля экземпляра, заданные в `constructor()`, а не константы на уровне модуля.
  - Значение, которое используется один раз и не меняется, оставлять инлайн-литералом, без имени.
- Названия (переменные, поля, методы, классы, файлы) должны быть говорящими: по имени сразу понятно, что это и зачем. Не использовать жаргон и сокращения, которые нужно расшифровывать. Если имя не объясняет себя, добавить короткий комментарий с назначением.
- Если поведение определяется дискретным состоянием (например, `dependency.state === "broken"`), проверять состояние напрямую. Не выводить его из косвенных признаков.
- TypeScript в `strict`-режиме с `noUncheckedIndexedAccess` и `exactOptionalPropertyTypes`. Весь код на `.ts`. `any` не использовать; если тип действительно неизвестен — `unknown` и проверка.
- Ошибки, которые ожидаемы по сценарию (папка не найдена, нет файлов, синтаксическая ошибка в файле), — это не исключения, а значения результата: функция возвращает результат, в котором есть ошибка. `throw` — только для действительно непредвиденных ситуаций.

## Конвенции проекта

- Кавычки двойные, точки с запятой обязательны.
- Отступ — 2 пробела.
- Экспорты только именованные (`export const`, `export class`, `export function`), без `export default`.
- Импорты с расширением `.js`, даже из `.ts`-файлов: `from "../shared/types.js"`.
- Комментарии на русском.
- Тесты рядом с кодом: `*.test.ts`. Для тестов Parser и Graph Builder — маленькие проекты-образцы в `test/fixtures/<название>/`.
- UML-диаграммы проекта (PlantUML) — в `docs/uml/`. Если меняется класс или его операции, обновить проектную диаграмму классов в том же коммите.

### Стили страницы графа

- Классы в БЭМ-стиле, в camelCase: корневой класс совпадает с именем блока (`.graphView`), элементы через `__` (`.graphView__node`).
- Порядок свойств в правиле: сначала позиционирование, затем раскладка, затем размеры, затем оформление. Группы можно отделять пустой строкой.
- Единицы только `px`.
- Палитра и шрифт — будут определены при создании Renderer; новые цвета не придумывать, если подходит существующий.

## Как работать

- Делать ровно то, что попросили. Не переписывать соседнюю логику и не «чинить» попутно ошибки типов, импорты или такие же баги в других местах.
- Если после точечной правки остаются связанные ошибки, упомянуть их одной строкой и ждать указаний.
- Если просят проверить или продиагностировать, только сообщать находки, ничего не править.
- После выполнения не предлагать следующие шаги и дополнительную работу.
- Если правка ограничена выделенным блоком или строками, не трогать другие блоки и файлы.
- Новую зависимость (npm-пакет) добавлять только после согласования: назвать пакет и зачем он нужен.
- Вспомогательные скрипты писать на JS (Node). Python в этом проекте не использовать.
